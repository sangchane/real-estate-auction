- 상태: **진행 중 (2026-07-29 착수)** — §3-1 수집기 구현 중
- 시작 전 필독: `AGENTS.md`, 이 문서 전체, `WP-02-auction-collector.md`(수집기 계약),

## 목적

우리 권리분석 룰이 실제로 맞는지 **시장의 실제 낙찰 결과로 역채점**한다. 로드맵 1-6의 완료 기준인
NF-01("검증 세트를 기존 유료 서비스 결과와 교차 검증")은 유료 서비스 구독이 필요해 미충족 상태다.
그 대신 **법원이 공개하는 실제 매각 결과**를 정답지로 삼는다.

사용자 가설(2026-07-29): *"좋은 물건은 보통 3회 안에 낙찰된다. 낙찰됐다는 건 여러 입찰자가 각자
권리분석을 하고 괜찮다고 판단했다는 뜻이다."*

## §1. 조사로 확정된 사실 (재조사 금지)

1. **낙찰자·응찰자수는 얻을 수 없다.** 대법원은 최고가매수신고인을 마스킹하는 게 아니라 필드
   자체를 제공하지 않는다. 사건 당사자내역은 전부 마스킹된다("최OO"). 응찰자수도 없다.
   → **"LH가 낙찰받은 물건"을 정답지로 쓰는 설계는 불가능하다.**

2. **LH는 물건을 고르지 않는다.** 전세사기피해자 지원 특별법 §25에 따라 LH는 피해자에게서
   **우선매수권을 양도받아** 경·공매에 참여한다. 제3자가 낙찰된 뒤 **그 낙찰가가 LH 매입기준가격
   이하일 때만** 우선매수권을 행사한다. 즉 LH가 붙은 물건은 "전문가가 고른 좋은 물건"이 아니라
   **전세사기·깡통전세 사고 물건**이다. → 양성 라벨이 아니라 **음성 라벨**로 써야 한다.

3. **낙찰가·결과코드는 얻을 수 있다.** 두 경로가 있고 각각 제약이 다르다.
   - 매각결과검색(`selectDspslSchdRsltSrch.on`): 대량. **기일 후 7일 윈도우만** 제공, 날짜 검색 없음.
   - 경매사건검색(`selectAuctnCsSrchRslt.on`): 사건 단위. 종국(배당종결, 매각 후 1~3개월) 전까지.
   결과코드: 001=매각, 002=유찰, 003=최고가매각허가결정, 009=납부, 010=미납, 014=변경, 015=배당종결.

4. **과거 소급 수집은 불가능하다.** 종국 사건은 조회 자체가 안 된다(실측 확인). **진행 중 물건을
   계속 추적해 앞으로 쌓는 수밖에 없다.** → 수집을 하루라도 빨리 시작할수록 표본이 커진다.

5. **공매(온비드)는 범위 밖이다.** 경매와 별개 제도·별개 시스템이다. LH는 공매에서도 우선매수권을
   행사하므로, 통계에 "공매로 간 건은 안 보인다"는 편향이 남는다(§5에 한계로 기록).

## §2. 가설 카탈로그 (검증 대상)

사용자 지적(2026-07-29): *"유찰횟수만으로 좋은 물건으로 보지 마라. 인수 부담이 있어도 그만큼
가격이 빠지면 메리트가 생겨서 낙찰된다."* — 맞다. 그래서 단일 지표가 아니라 아래를 각각 잰다.

실무 공식(외부 자료 교차 확인):
```
인수금   = 대항력 있는 임차인의 보증금 − 실제 배당액
실투자금 = 낙찰가 + 인수금 + 명도비 + 취득세 + 수리비
안전마진 = 실투자금이 시세의 80~85% 이내
유찰 저감 = 회차당 20% (최저가율 100% → 80% → 64% → 51.2%)
낙찰가율 참고치 = 아파트 85~95% / 빌라·다세대 75~85% / 상가 70~80%
```

| ID | 가설 | 측정 가능한 예측 | 필요 데이터 | 지금 가능? |
|---|---|---|---|---|
| H1 | 유찰이 늘수록 낙찰가율이 낮다 | 유찰횟수와 낙찰가율에 음의 상관 | 결과+감정가 | **가능** |
| H2 | 우리가 계산한 인수액이 클수록 낙찰가율이 낮다 | 인수액↑ → 낙찰가율↓ (음의 상관) | + 등기부 | 등기부 필요 |
| H3 | 대항력 임차인 존재 자체가 낙찰가를 낮춘다 | 임차인 有 더미변수가 음의 계수 | + 명세서 | 명세서 필요 |
| H4 | 총부담액(낙찰가+인수액)은 시세의 80~85%로 수렴한다 | 인수액이 커도 총부담액 비율은 일정 | + 시세 | 실거래가 API 필요 |
| H5 | 우리가 "인수 0건"이라 한 물건은 조기 낙찰된다 | 유찰 0~2회 내 낙찰 비율이 유의하게 높음 | + 등기부 | 등기부 필요 |
| H6 | 당해세를 반영하면 예측이 개선된다 | 당해세 반영 전/후 H2 상관계수 비교 | + 세금 압류 | 등기부 필요 |
| H7 | LH 우선매수 개입 물건은 우리 룰이 고위험으로 판정한다 | 음성 라벨 재현율 | + 명세서 비고란 | 명세서 필요 |
| H8 | **관심등록 증가 속도**가 낙찰 여부·낙찰가율을 예측한다 | 유찰횟수 통제 후에도 유의한 양의 계수 | 관심등록 시계열 | **추가 수집 불필요** |

**H1이 베이스라인이다.** 우리 룰 없이 유찰횟수만으로 낙찰가율을 얼마나 설명하는지 먼저 잰다.
그 위에 우리 룰의 인수액을 넣었을 때 **설명력이 올라가야** 룰에 가치가 있다. 올라가지 않으면
룰이 시장 판단에 아무것도 더하지 못한다는 뜻이다.

선행연구 참고 — 서울 아파트 낙찰 460건 다중회귀(R²=0.398): 유찰횟수 β=−0.168,
**임차인 유무 β=−0.415(가장 큰 음의 영향)**, 매각물건층 +0.155. 서울 아파트 평균 유찰 0.5회.
→ H3의 방향과 크기에 대한 사전 기대치로 쓴다.

## §4. 배당 순서 교정 (당해세 — 현재 엔진의 실제 결함)

현재 `apps/api/src/rights-analysis/domain/distribution.ts`의 순서:
```
경매비용 → 최우선변제(소액임차인) → 우선변제(확정일자·등기접수일 순)
```
**당해세 단계가 통째로 빠져 있다.** 올바른 순서:
```
경매비용 → 최우선변제(소액임차인) → 당해세 → 우선변제 → 일반채권 안분
```
결과적으로 **당해세가 있는 물건에서 인수액을 실제보다 적게 계산한다.**

추가로 **채권 종류별 순위 비교 기준일이 서로 다르다** — 지금 엔진은 등기 접수일 하나만 쓴다.

| 채권 | 순위 비교 기준일 |
|---|---|
| 임차인 우선변제권 | 대항요건(인도+전입)과 확정일자를 **모두** 갖춘 시점 |
| 조세채권 | 세목별 **법정기일** (등기일 아님) |
| 4대 보험료 등 | 각 채권의 **납부기한** |
| 근저당 등 담보물권 | 등기 설정일 |

당해세 = 그 부동산 자체에 부과된 세금. 국세(종부세·상속세·증여세), 지방세(재산세·지역자원시설세 등).
소득세·부가세·취득세는 당해세가 **아니다**(일반 조세, 법정기일로 순위 결정).

**2023-04-01 특례**: 임차인 확정일자보다 법정기일이 **늦은** 당해세는 그 금액만큼 임차인에게 먼저
배당한다. 확정일자보다 **앞선** 당해세는 여전히 임차인보다 우선한다. 주택임대차보호법상 임차인에게만
적용(상가 제외).

### 구현 완료 (2026-07-30) — `DISTRIBUTION_TABLE` v2

배당 순서를 교정했다. `TaxClaim`(id·isPropertyTax·statutoryDate·amount?)을 신설해 등기 권리와
분리했다 — **조세는 등기 접수일이 아니라 법정기일로 순위를 다투기 때문**이다.

- 당해세(`isPropertyTax: true`) 단계를 최우선변제와 우선변제 **사이**에 추가
- **2023-04-01 특례** 반영: 임차인 확정일자보다 법정기일이 **늦은** 당해세는 그 금액만큼 임차인에게
  먼저 배당. `saleDecisionDate`로 시행일 전후를 가르고, 없으면 현재 사건으로 보아 특례를 적용한다
- 일반 조세(`isPropertyTax: false`)는 우선변제 단계에서 **법정기일**로 순위 경쟁
- 금액 미상은 배당에서 제외하고 `unknownAmountTaxClaimCount`로 노출 → **인수액이 하한임**을 표시
- `taxClaims`를 넣지 않으면 기존 결과가 그대로다(회귀 테스트로 강제)

검증: API 338 테스트 통과(기존 331 회귀 없음, 신규 7). 대표 케이스 —
낙찰대금 2억·보증금 2억·당해세 5천만(법정기일이 확정일자보다 앞섬) → 임차인 1.5억 배당,
**인수액 5천만원**. 같은 조건에서 당해세를 빼면 인수액 0원. 즉 v1은 이 5천만원을 놓치고 있었다.

**금액을 알 수 없는 게 정상이다.** 외부에서 당해세 체납액을 정확히 알 방법이 없다. 그래서:
- 금액이 주어지면 배당에 반영한다.
- 금액을 모르는데 세금 압류(갑구 "압류 국-○○세무서" / "압류 구-○○구청")가 있으면,
  인수액을 **하한**으로만 제시하고 `NEEDS_REVIEW`로 표시한다. 확정적 금액을 지어내지 않는다.
- 대항력 임차인 + 세금 압류 조합은 특히 위험하다(실무 원칙: 금액 파악 전 입찰 보류).

관심등록이 54건으로 표본 중 압도적 1위였다. 오래 유찰되던 물건이 갑자기 경쟁이 붙은 건이라
**우리 룰이 설명해야 할 대표 사례**다(H2·H5의 좋은 검증 대상).

### H8 주의 — 관심등록 절대값은 쓰지 마라 (실측)

사용자 착안(2026-07-29): *"관심등록이 많이 된 물건일수록 괜찮은 물건일 수 있겠다."*
데이터로 재보니 **관심등록 절대값은 유찰횟수의 대리변수였다.**

| 유찰 | 17 | 12 | 9 | 3 | 2 | 2 | 1 | 1 |
|---|---|---|---|---|---|---|---|---|
| 관심등록 | 57 | 16 | 54 | 6 | 6 | 5 | 3 | 2 |
| 낙찰가율 | 2.3% | 7.3% | 65.8% | 63.8% | 65.6% | 64.9% | 81.8% | 138.5% |

관심등록은 **노출 기간에 비례해 누적**된다. 오래 유찰된 물건일수록 관심이 쌓이고, 그 물건은
낙찰가율이 낮다. 그래서 통제 없이 재면 "관심 많음 → 낙찰가율 낮음"이라는 **역방향 결론**이 나온다.

→ **절대값이 아니라 증가 속도(Δ관심등록/Δ일)로 재고, 유찰횟수를 통제하라.**
`auction_item_raw`에 관측 이력이 이미 쌓이므로 수집을 계속 돌리면 계산 가능해진다.
현재는 물건당 관측이 2회뿐이라 산출 불가.

참고: 조회수(`inqCnt`)는 표본 8건 중 5건이 0이라 신뢰도가 낮다. 관심등록(`gwansMulRegCnt`)만 쓴다.

## §4-2. 수집·집계에서 반드시 지킬 것 (실측으로 확인된 함정)

1. **낙찰가율은 `auction_sale_result.minimum_sale_price`(그 기일 최저가)로 계산하라.**
   `auction_item.minimum_sale_price`는 최신 관측값이라 낙찰 시점과 다르다. 이걸 쓰면
   "낙찰가 < 최저가" 같은 불가능한 값이 나온다(실제로 나왔다).

2. **일괄매각 사건은 물건 단위로 세지 마라.** 같은 사건의 여러 물건이 **감정가·최저가·낙찰가를
   동일하게** 가진다(`groupmaemulser` 동일). 실측: `2024타경119676`(물건1,2),
   `2024타경121396`(물건1,2), `2025타경304`(물건1,2). 물건 단위로 집계하면 이 사건들이
   중복 계상돼 통계가 왜곡된다. **사건 단위로 dedupe할 것.**

3. **한 사건의 물건을 일부만 보유할 수 있다.** 수집이 매각기일 2주 창으로 제한돼 있어,
   일괄매각 사건의 물건 일부만 우리 DB에 있을 수 있다. 이 경우 낙찰가(전체)를 개별 물건
   감정가로 나누면 비율이 부풀려진다.

4. **물건번호 ≠ 목적물번호.** 사건검색의 `dspslGdsSeq`는 물건번호(`maemulSer`)이고 우리
   `item_no`는 목적물번호(`mokmulSer`)다. 물건별 목록의 `dspslObjctSeq`로 매핑해야 한다
   (`2024타경109389` 실측: 물건2 = 목적물3). **이걸 틀리면 다른 물건에 결과가 붙는다.**

5. **`UNIQUE` 제약의 NULL 함정.** 마이그레이션 004의 `UNIQUE (..., result_code, sale_amount)`는
   PostgreSQL이 NULL을 서로 다른 값으로 취급해 유찰 행(낙찰가 NULL) 중복을 못 막는다.
   현재는 저장소의 `IS NOT DISTINCT FROM` 검사로 멱등을 보장한다. PG 18이므로 나중에
   `NULLS NOT DISTINCT`로 정리 가능하다(미적용).

### 좌표 기반 표 복원 (`notice_tenant_parser.py`)

`notice_document_unavailable`을 남기고 기재사항만 저장한다. 재수집 시 점유자 표는 **통째로 교체**하되,
`--with-tenants` 없는 실행이 이미 받아둔 표를 지우지 않는다.

## §4-7. 점유자 표 파싱 수율 — 검증 게이트 도입 (2026-07-30)

**표본을 늘리자 파싱이 무너졌다.** 문서 2건에 맞춰 튜닝한 좌표 기반 표 복원이 10건에서는
셀 조각을 별개 행으로 쪼갰다 — 실측: 20행 중 `505호(`·`시`·`605호)`·`공부상`·`실제표` 같은
조각 15행. 전입일이 있는 행은 3행뿐이었다. 이 20행은 DB에서 삭제했다.

**검증 게이트를 넣었다** (`_is_usable`): `source_kind`가 정상값 3종(현황조사·권리신고·
등기사항전부증명서) 중 하나여야 하고 — 행 경계가 제대로 잡혔다는 신호 — 그 위에 전입일이나
보증금이 하나라도 있어야 저장한다. 못 갖춘 행은 저장하지 않고 세기만 하며,
러너 로그에 `tenants_rejected=N`으로 드러난다. **쓰레기를 DB에 넣는 것보다 낫다.**

재수집 결과: `items=10 parsed=10 tenants=3 tenants_rejected=17` — **수율 15%.**
저장된 3행은 깨끗하고 그중 1행은 완전하다(권리신고 · 505호 · 5,000만원 · 전입 2002-02-02 ·
확정일자 2002-02-19 · 배당요구 O).

**H3·H5에 그대로 쓸 수 없는 이유 — 거부된 행은 "임차인 없음"과 구분되지 않는다.**
파싱이 실패한 물건은 임차인이 없는 것처럼 보인다. H3(임차인 존재가 낙찰가를 낮추는가)은
임차인 유무의 신뢰도가 전제라, 수율을 올리기 전에는 **물건별 `rejected>0`을 "파싱 불신"으로
표시해 표본에서 제외**해야 한다. ~~현재 스키마에는 그 표시가 없다 — 다음 작업.~~
→ **해결 (2026-08-07, §4-23)**: `tenant_rows_rejected` 컬럼(013)으로 표시한다.

## §4-8. 점유자 표 파싱 수율 개선 (2026-07-30) — 15% → 75%

**원인은 점유부분이 행 기준선(anchor)이었던 것.** `공부상 505호(실제표시 605호)`가 5줄로
감싸이면서 각 줄이 가짜 기준선이 돼 3행짜리 표가 9행으로 쪼개졌다. 점유부분을
`_ANCHOR_FIELDS`에서 빼고 **금액·날짜만** 기준선으로 쓴다 — 이 컬럼들은 감싸지지 않아
행마다 정확히 한 줄이다.

**핵심 발견: 셀은 행 상자 안에서 세로 중앙정렬로 렌더된다.** 기준선(한 줄 컬럼 값)이 곧 행의
세로 중앙이므로 위 경계가 `b`면 **아래 경계는 `2×기준선 − b`** 로 닫힌다. 이 기하학적 모델로
실측 6문서 + 기존 fixture의 행 경계가 전부 정확히 복원된다. 종전의 "가장 가까운 기준선에 붙이기"는
키 큰 행의 첫 줄이 1~2pt 차이로 위 행에 붙는 구조적 결함이 있었다.

**부수 발견**: 빈 표는 `조사된 임차내역없음` 한 줄이 표를 가로질러 렌더돼 문서마다 가짜 거부 행을
1건씩 만들고 있었다. 이는 행이 아니라 법원의 명시적 "점유자 없음"이라 파싱 대상에서 제외했다 —
§4-7의 "`rejected>0`을 파싱 불신 신호로 쓴다"는 계획에도 이 구분이 필요하다.

기각된 가설: 컬럼 x 경계 어긋남(실측 7문서 전부 동일 — 고정 경계 유지). 미관찰: 전 컬럼 공란 행
(모든 점유자 행이 금액·날짜에 최소 `미상`을 적어 기준선이 생겼다).

### 수율 (같은 표본, 서울동부 1페이지)

| | 저장 | 거부 | 수율 |
|---|---|---|---|
| before | 3 | 15~17 | 15~17% (저장분 중 2건도 오염) |
| **after** | **3** | **1** | **75%** |

거부 1건은 전입일·보증금이 **모두 `미상`인 진짜 임차인 행**으로, 게이트 설계대로 거부됐다
(엔진 `Tenant`의 필수값이 없다). 저장된 3행은 문서와 완전히 일치한다 —
`공부상 505호(실제표시 605호)`가 조각나지 않고 온전히 복원됐다.

fixture 7건을 확보해 문서별 기대값 테스트를 붙였다. **사람 이름은 가명으로 치환**했다
(좌표·길이 보존). 정규식이 아니라 문서별로 눈으로 확인한 뒤 전체 문자열 치환이다.

### rowspan 병합 성명 — 해결 (2026-07-31)

같은 점유자가 정보출처별로 여러 행에 걸칠 때(rowspan) **성명은 병합 셀에 한 번만 렌더된다.**
따라서 성명이 없는 행은 직전 점유자의 연속이다. 종전에는 그런 행에 **행 순번**을 줘서
동일인이 여럿으로 갈렸다(실측: 현황조사 seq 2 / 권리신고 seq 3이 같은 사람).

→ 성명이 없으면 **직전 순번을 잇는다**. 첫 행부터 성명이 없으면 이을 앞 행이 없으므로 새 순번을 연다.

검증: 물건 106의 두 행이 같은 `seq=2`를 공유하고 임차인 수가 **1명**으로 집계된다.
서로 다른 성명은 각자 다른 순번을 받는지도 테스트로 강제했다(연속 규칙이 다른 사람까지
묶으면 안 된다).

## §4-9. 연결 표본 첫 확보 시도 (2026-07-30)

사용자 질문: *"강동구 아니어도 매각 결과 수집해서 테스트해볼 방법 없나?"*

**소급 경로는 막혔다.** 결과가 이미 있는 물건에 명세서를 뒤늦게 받으려 했으나, 기일이 지난
물건은 물건상세가 빈 객체로 온다(§4-3 정정). 결과→명세서 방향은 불가능하다.

**대신 반대 방향이 됐다.** 명세서를 이미 가진 물건 중 기일이 그날(7/30)인 서울중앙 10건을
찾아 `backfill`로 결과를 채웠다. **연결 표본 10건 확보.**

다만 **10건 전부 유찰(`002`)** 이라 낙찰가가 없어 H2·H5의 낙찰가율은 아직 못 잰다.
유찰 표본도 버리는 데이터가 아니다 — H5("인수 없음이라 한 물건이 조기 낙찰되는가")의
반대 방향 증거로 쓰인다.

**다음 관문**: 서울동부 명세서 보유 물건의 기일이 **8/3에 103건, 8/10에 89건** 몰려 있다.
유찰률을 감안하면 8/3분에서 낙찰 20~30건이 나올 것으로 보이고, 그 정도면 H2·H5를 처음으로
실측할 수 있다.

## §4-10. 법원 서버의 소프트 스로틀 (2026-07-31 실측) — 재조사 금지

**법원은 요청이 쌓이면 403/429가 아니라 빈 응답으로 조용히 degrade한다.**

실측: `daily` 한 번에 물건 467건의 명세서를 훑었더니 **180건이 연속 정상, 이후 287건이 연속으로
`dspslGdsDxdyInfo` 없는 응답**이었다. 실패는 분당 ~35건(요청간격 그대로)으로 균일했고, 무작위로
섞이지 않고 시간축에서 딱 갈렸다. **3시간 뒤 같은 물건을 조회하니 정상**(`gdsSpcfcWrtYmd=20260708`),
재실행에서 287건 전부 `notice_unavailable=0`으로 수집됐다.

- HTTP 상태코드는 정상이라 `BlockedByCourtError`(403/429)가 안 걸린다.
- 그래서 `notice_unavailable`은 **"아직 미작성/기일 지남"과 "스로틀당함"을 구분하지 못한다.**
  이 숫자를 "명세서 영구 없음"으로 읽으면 안 된다.
- 기각된 가설: `srchRowIndex` 불일치(row_index 0·5·9·10·37·350 전부 정상 — 무관하다).
- 영구 손실은 아니다. 스로틀당한 물건은 명세서 행이 안 생겨 다음 실행이 다시 시도한다.

**대응 — 기일이 가까운 물건부터 훑는다.** 검색 순서대로 돌면 스로틀 벽 너머로 밀린 물건이 그날
통째로 누락되는데, 하필 8/3·8/10 기일 물건이 뒤쪽이라 **가장 급한 것이 가장 먼저 버려졌다**.
`run_daily`가 `maeGiil` 오름차순으로 정렬한다. `notice_limit` 상한도 급한 것부터 남긴다.

## §4-11. 점유자 표 고유키 결함 (2026-07-31) — 명세서 467건 유실

005는 `tenant_seq`를 "물건 내 행 순번"으로 두고 `UNIQUE (notice_id, tenant_seq, source_kind)`를
걸었다. **§4-8에서 rowspan을 고치며 `tenant_seq`의 의미가 동일인 순번으로 바뀌었는데 제약이
그대로 남았다.** 그래서 한 사람이 같은 정보출처로 두 행을 갖는 문서를 저장할 수 없다.

실측: 현재 표본에 그런 묶음이 **52건** 있다(예: HUG가 등기사항전부증명서로 임차권등기 2건).

두 번째 결함이 피해를 키웠다 — 명세서 저장이 배치 단위 트랜잭션이라 **중복키 1건이 그 법원
배치 전체를 되돌렸다**. `detailed=467 parsed=0`, 70분·2,382요청이 통째로 버려졌다.

- 마이그레이션 010: 고유키를 문서상 행 순서(`row_no`)로 바꿨다. 멱등성은 원래 이 제약이 아니라
  저장소의 "notice별 통째 삭제 후 재삽입"이 보장하고 있었다.
- `upsert_notices`가 명세서 건마다 savepoint를 잡는다. 실패 수는 `store_failed=N`으로 드러낸다 —
  안 세면 "받아왔는데 저장 안 됨"이 로그에서 성공처럼 보인다.

## §4-13. 기일이 바뀌면 명세서를 다시 받는다 (2026-08-02)

**명세서는 기일마다 새로 작성된다.** 실측: 명세서 467건의 작성일이 7/13~7/23에 몰려 있고
기일은 8/3~8/11이다 — 기일 약 2주 전에 작성된다. 물건당 명세서는 정확히 1건씩이었다.

그런데 daily의 명세서 단계는 **"명세서가 한 건이라도 있으면" 건너뛰었다.** 그래서 유찰로 새 기일을
받은 물건의 새 명세서와 새 점유자 표를 영영 받지 못한다. 유찰이 반복되는 물건일수록 첫 스냅샷에
영원히 묶이는데, 하필 §4-1 표본에 유찰 9·12·17회 물건이 있다. 기일 사이에 권리신고·배당요구가
추가되면 인수액 계산의 입력이 바뀌므로 백테스트에 그대로 영향을 준다.

`auction_item_notice.bid_date`(011)로 **어느 기일의 명세서인지** 기록하고, daily의 스킵 판단을
`(물건, 기일)` 단위로 바꿨다. `tenant_scanned_at`도 명세서 행마다 붙으므로 새 기일 명세서는
점유자 표를 새로 받는다 — 두 조건이 자연히 맞물린다.

기일을 모르는 검색 행(`maeGiil` 없음)은 예전처럼 유무로만 판단한다. 매일 다시 받는 것보다 낫다.

검증: 기일 그대로면 `skipped_existing=457 detailed=0 requests=0`(낭비 없음), 기일이 바뀌면
다시 받는 것을 회귀 테스트로 고정했다(고치기 전 코드로는 실패한다).

**이 결함은 §4-8·§4-13이 같은 유형이다** — 상위 리소스(명세서)가 있다는 이유로 하위·후속
리소스(점유자 표 / 다음 기일 명세서)가 없는 걸 못 보는 스킵 조건이다. 스킵 조건을 새로 넣을 때는
"무엇이 있으면 건너뛰는가"가 아니라 **"무엇을 이미 가졌는가"**를 키로 잡아야 한다.

## §4-14. 매각결과는 당일 오전에 없다 — 스케줄 19:00 (2026-08-03 실측)

매각기일 입찰은 10:00인데 스케줄이 07:00이라 매각결과 단계가 매번 하루 늦었다
(`sale_result_backfill_done pending=0`). 같은 날 12:58에 두 경로를 다 확인했지만 **8/3 결과는
아직 공개 전**이었다.

| 경로 | 그날 돌려준 것 |
|---|---|
| `backfill`(경매사건검색) | 과거 기일 이력만 (8/3 없음) |
| `sweep`(매각결과검색, 7일 윈도우) | **7/27 기일** 결과 — 최신 완료 회차이지 당일이 아니다 |

→ 스케줄을 **19:00**으로 옮겼다. 명세서는 기일 1주 전부터라 시각에 덜 민감하다.

**재시도가 되는지 확인했다(중요)**: `backfill`이 과거 기일 79건을 넣었지만 대기 물건은 99건 그대로다.
대기 판정이 "그 기일 **이후** 날짜의 결과 행이 있는가"라서 과거 행으로는 해소되지 않는다. 이게
아니었다면 과거 이력이 들어온 순간 8/3 결과를 영영 안 찾게 된다.

**미확인**: `daily`는 `backfill`만 돌고 `sweep`은 안 돈다. 사건검색이 결과를 결국 준다는 전제인데,
매각결과검색은 기일 후 7일만 제공하므로(§1-3) 사건검색이 놓치는 게 있으면 그 창을 지나 못 받는다.
8/3 결과가 backfill로 들어오는지 보고, 안 들어오면 daily에 sweep 단계를 넣어야 한다.

**부수 발견 — §5의 "과거 유찰 이력 백필 불가"는 재검토 대상이다.** 사건검색이 과거 기일 79건을
돌려줬다(2026-06-15 한 기일에만 68건). 기일별 최저가 추이를 앞으로만 쌓을 수 있다고 본 전제가
생각보다 느슨할 수 있다.

## §4-15. 유찰횟수를 무엇으로 설명할 수 있나 (2026-08-04 실측, 469건)

지도 클러스터에 "지역 평균"을 얹을지 검토하며 잰 결과다. **집계 축으로 쓸 만한 것이 없다**는 결론.

사용자 지적(2026-08-04): *"어느 동네가 싼가는 의미가 없다. 매물 권리 상태에 따라 유찰되는 게
영향이 크다."* — 이 가설을 재봤는데 **현재 표본에서는 확인되지 않았다.**

### 유찰횟수 평균의 분산 폭

| 축 | 최소 | 최대 | 폭 |
|---|---|---|---|
| 인수권리 유형 | 임차권등기 2.02 | OTHER 2.75 | **0.7회** |
| 시군구 | 서초 0.93 | 종로 4.21 | **3.3회** |
| 용도 | 단독주택 1.24 | 임야 6.00 | **4.8회** |

인수권리 유형별로는 거의 평평하고, **임차권등기 있는 물건(2.02)이 인수권리 `NONE`(2.34)보다
오히려 덜 유찰됐다.**

### 왜 뒤집혀 보이나 — HUG가 `NONE`을 오염시킨다

| HUG 포기확약 | 인수권리 | 물건 | 평균유찰 |
|---|---|---|---|
| **있음** | `NONE` | 35 | **2.77** |
| 없음 | `LEASEHOLD_REGISTRATION` | 66 | 2.02 |
| 없음 | `NONE` | 68 | 2.12 |

§4-4 그대로다 — **HUG 물건은 임차권등기가 있어도 법원이 인수권리를 `NONE`으로 적는다**(포기확약
때문에). 그래서 전세사기 사고 물건이 `NONE` 그룹에 섞여 평균을 끌어올린다.
**인수권리 유형 코드만으로는 위험을 가를 수 없다.**

### 지역 평균은 두 가지 대리변수다

1. **용도 구성**: 종로구 4.21회는 지역 특성이 아니라 상가·오피스텔이 몰린 결과로 보인다
   (오피스텔 평균 4.49회).
2. **가격 수준**: 사용자 지적대로 지역별 시작가 차이가 애초에 크다 —
   평균 감정가가 **서초 181억 / 강남 43억 / 관악 5.3억 / 강동 4.0억**으로 45배 벌어진다.
   지역 평균 하락률을 지도에 얹으면 이 구성 차이를 물건의 성격처럼 보여주게 된다.

### 결론

- 클러스터는 **개수 표기를 유지한다.** 지역 집계는 오해를 부르고, 권리 집계는 신호가 안 잡힌다.
  (조사에서 확인한 "한국 부동산 앱은 개수 클러스터를 안 쓴다"는 관용과는 어긋나지만, 대체할
  집계 축이 신뢰할 만해진 뒤에 바꾸는 게 맞다.)
- **가설을 기각한 것은 아니다.** 우리가 가진 인수권리 코드는 너무 거칠고(공란 257건), 진짜 신호인
  **인수 금액**은 등기부(CODEF)가 있어야 나온다. H2·H3가 풀려는 문제가 정확히 이것이다.
- 상관이지 인과가 아니고, 표본이 서울 2개 법원 469건이다.

## §4-16. 후보 필터와 그 결과 (2026-08-04)

사용자 착안: *"권리분석상 좋은 물건이면 입찰자가 많고 유찰도 적을 것"*. 그 반례 —
**인수 부담이 없는데 유찰이 쌓인 물건** — 을 뽑아 8/11 이후 낙찰 여부로 채점한다.
지금 뽑아둬야 결과를 보고 가설을 맞추는 사후 편향이 없다. 리포트에 섹션으로 고정했다.

조건 충족: 인수권리 `NONE` 103건 / HUG 포기확약 76건, 그중 유찰 3회 이상이 각각 35·36건.

**결과가 가설을 지지하지 않는다 — 후보의 거의 전부가 HUG 전세사기 사고 물건이다.**
인수 위험이 0인데도(§4-4의 검증된 규칙) 시장이 11회까지 외면했다. 즉 "시장이 못 알아본 물건"이
아니라 **"다른 이유로 기피하는 물건"**일 가능성이 높다. 짚이는 이유:
- **명도 부담** — 점유자가 2~3명씩 있다. 인수 금액이 없어도 내보내는 비용·시간은 매수인 몫이다.
- **용도** — 오피스텔·상가·연립주택이 대부분. §4-15대로 이 용도가 원래 유찰이 많다(오피스텔 4.49회).
- 명세서 플래그로 안 잡히는 것(입지·노후·수익성).

가장 설명이 안 되는 한 건: **2024타경61978 아파트, 유찰 8회, 최저가율 21%, 점유자 1명,
인수권리 `NONE`(법원 명시), 위험 플래그 0건.** 아파트는 평균 유찰 1.31회로 가장 적은 용도다.
우리 데이터로 설명되지 않으므로 이 물건 자체가 검증 대상이다.

### 재감정 함정 (신규 발견)

**유찰 11회인데 최저가율 100%인 물건이 있다**(`2024타경122368`: 감정가 2.6억 = 최저가 2.6억).
여러 번 유찰된 뒤 법원이 재감정해 최저가를 새 감정가로 되돌리면 `failed_bid_count`만 누적으로
남는다. 유찰 3회 이상 172건 중 **22건**이 최저가율 90% 이상이다.

→ **유찰횟수를 "얼마나 싸졌나"의 대리지표로 쓰면 이 22건에서 틀린다.** 최저가율을 함께 봐야 한다.
H1의 해석에도 영향을 준다.

낭비도 5배가 되므로 이 장치가 없으면 매 실행이 수천 요청을 헛돈다.

### §4-20. 첫 채점 — 인수 부담이 낙찰률을 가른다 (2026-08-05)

사용자 가설(§4-17): "권리분석상 좋은 물건이면 입찰자가 많고 유찰이 적을 것."
응찰자 수는 못 받으므로(§4-18) **낙찰 여부**를 대리지표로 썼다.

**먼저 세는 단위를 바로잡아야 한다.** 처음 채점할 때 목적물마다 세었는데, 일괄매각은 사건
하나가 한 번 팔리는 것이라 낙찰 사건 4건이 목적물 23건으로 부풀었다(낙찰률 30.3%로 관측).
"임야 낙찰률 93.8%"도 같은 착시였다 — 목적물 16개가 사건 2건이었다.
**일괄이면 사건당 1건, 아니면 목적물당 1건**으로 센다(`sale_unit` 뷰).

**두 번째로 바로잡을 것은 관측 창이다.** 결과는 전량 `CASE_SEARCH` 출처이고 최초 관측이
2026-07-31이다. 그 전 기일은 **생존 편향** 때문에 못 쓴다 — 팔린 사건은 공고 목록에서 빠지므로
우리 물건 목록에 없고, 사건검색으로 과거를 훑으면 **안 팔린 사건의 유찰만** 남는다.
실측이 그대로 보여준다.

| 기일월 | 낙찰 | 유찰 |
|---|---|---|
| 2026-06 | **0** | 331 |
| 2026-07 | 1 | 29 |
| 2026-08 (관측 후) | 92 | 207 |

6월에 유찰 331건인데 낙찰이 0건인 것은 시장 현상이 아니다. 이 구간을 섞으면 낙찰률이
통째로 과소평가된다. **`dxdy_date >= 2026-07-31`로 제한한다.**

표본: 관측 창 안에서 결과가 붙은 **165 매각단위**.

| 구분 | 매각단위 | 낙찰 | 낙찰률 | 낙찰가율 |
|---|---|---|---|---|
| 인수 부담 없음 | 89 | 22 | **24.7%** | 89.9% |
| 인수 부담 있음 | 76 | 9 | **11.8%** | 88.9% |

z≈2.1, p≈0.035. 제한 전(27.0% vs 8.7%, p≈0.0005)보다 **효과도 작고 확신도 낮다.**
방향은 유지되지만 "세 배 차이"는 편향이 부풀린 값이었다.

**가설의 절반만 맞았다.**

- 맞은 쪽: 인수 부담이 없으면 두 배쯤 잘 팔린다. **주거만 떼어 봐도 유지된다**
  (28.2% vs 11.3%, 각 71단위). 비주거는 23단위뿐이고 그중 부담있음이 5단위라 판단하지 않는다.
- 틀린 쪽: **유찰 횟수는 낙찰률을 예측하지 못한다.** 0회 22.2%(45) / 1회 25.4%(59) /
  2회 30.2%(53) / 3회 23.8%(42) / 4회 이상 32.4%(68)로 단조적 관계가 없다. 굳이 방향을
  읽으면 유찰이 많을수록 조금 더 팔리는 쪽이라 **가설과 반대**다 — 많이 유찰돼 싸진 것이
  가격 매력으로 작용한 것으로 보인다.

**낙찰가율은 두 그룹이 같다**(89.9% vs 88.9%). 인수 부담은 "팔리느냐"를 가르지 "얼마에 팔리느냐"는
가르지 않는다.

**이 분석은 세 번 고쳤다.** 처음 낸 수치가 셋 다 틀렸다는 뜻이라 기록해 둔다.

1. `assumed_rights_kind IS NOT NULL` 필터가 HUG 물건 절반을 걸러냈다 (표본 93 → 43).
2. 목적물마다 세어 일괄매각 사건 하나가 목적물 수만큼 부풀었다 (일괄 낙찰률 30.3%, 임야 93.8%).
3. 관측 시작 전 기일을 포함해 생존 편향이 들어갔다 (27.0% vs 8.7% → 24.7% vs 11.8%).
4. 3을 고친 뒤에도 **하위 표(유찰·용도·교차)를 옛 수치 그대로 적어뒀다.** 화면을 붙이고
   나서야 터미널과 숫자가 다른 걸 보고 알았다.

넷 다 **낙찰률을 계산하는 분모·분자를 잘못 잡은 것**이다. 앞으로 이 표를 볼 때 표본 수가
갑자기 뛰거나 특정 그룹만 유난히 좋으면 단위·필터·기간부터 의심한다. 화면(`/admin/backtest`)과
터미널 리포트가 **같은 정의**를 쓰므로, 두 곳 숫자가 다르면 한쪽이 낡은 것이다.

### §4-21. 후보 필터 재작성 (2026-08-05)

§4-17에서 만든 "인수 부담 없음 + 유찰 3회 이상" 필터의 두 조건 중 **유찰 조건은 채점에서
지지되지 않았다.** 빼고 다시 짰다. 채점 3의 교차표가 근거다.

| 인수 부담 | 최저가율 | 매각단위 | 낙찰 | 낙찰률 |
|---|---|---|---|---|
| 없음 | 70% 이상 | 61 | 20 | **32.8%** |
| 있음 | 70% 이상 | 40 | 8 | 20.0% |
| 없음 | 70% 미만 | 28 | 2 | 7.1% |
| 있음 | 70% 미만 | 36 | 1 | **2.8%** |

(관측 창 기준. 처음 적었던 값은 창 제한 전이라 70% 미만 구간이 실제보다 좋아 보였다 —
없음 14.3% → 7.1%, 있음 3.0% → 2.8%.)

두 구간을 각각 뽑되 **"좋은 물건"이라 부르지 않는다** — 낙찰률이 높다는 건 경쟁이 붙는다는
뜻이지 싸게 살 수 있다는 뜻이 아니다.

- **후보 A** (부담 없음 + 70% 이상, 실측 32.8%): 값이 붙는 구간.
- **후보 B** (부담 없음 + 70% 미만, 실측 7.1%): 권리는 깨끗한데 안 팔린다. 기피 이유가
  명세서 밖에 있다는 뜻이다 — 명도·입지·건물 상태를 직접 확인해야 한다. §4-17이 노렸던
  "숨은 물건"은 정의상 이쪽이지만, 실측 낙찰률이 낮다는 것은 시장이 이미 이유를 알고 있을
  가능성도 같이 뜻한다.
- **가장 안 팔리는 구간**은 부담 있음 + 70% 미만이다(36단위 중 1건). 유찰이 쌓여 싸 보여도
  인수 부담이 있으면 계속 안 팔린다.

### §4-25. 기일 종류(01/02)와 결과 도착 시점 (2026-08-11 실측)

"8/10 기일 표본이 왜 안 들어왔나"를 점검하다 두 가지를 확정했다.

**① `auction_sale_result`에는 매각기일이 아닌 행도 섞여 있다.** 사건검색

### §4-26. 배당요구 공란을 "안 함"으로 읽지 않기로 했다 (2026-08-11)

`demanded_distribution` 값 분포가 **NULL 4,108 / true 2,617 / false 0**이었다. 대항력이 있어도
`ASSUMED_FULL`(보증금 전액 인수 확정)이 거의 안 잡히고 화면이 "인수 금액 확인 필요"만 보여주는
원인이라, 명세서의 빈 배당요구 칸을 `false`로 기록할지 검토했다. **채택하지 않았다.**

**1) 공란은 대부분 "이 출처에는 그 칸이 없다"다.** `source_kind` × 값 실측:

| source_kind | true | NULL |
|---|---|---|
| 권리신고 | 2,599 | 11 |
| 현황조사 | 0 | 2,541 |
| 등기사항전부증명서 | 7 | 1,534 |

배당요구여부는 권리신고 행에만 적히는 칸이다(true 2,617의 99.3%가 권리신고 행). 현황조사·등기
행 4,075건의 NULL을 false로 바꾸면 **칸이 없는 행에 "안 했다"를 새기는 것**이 된다.

**2) 행 단위 false는 자기모순을 만든다.** `(notice_id, tenant_seq)`=사람 단위로 묶으면:

| 그 사람에 true 행 있음 | NULL 행 있음 | 묶음 | NULL 행 수 |
|---|---|---|---|
| 아니오 | 예 | 2,311 | 2,495 |
| 예 | 아니오 | 1,267 | 0 |
| **예** | **예** | **1,337** | **1,613** |

마지막 줄이 결정적이다 — NULL 4,108건 중 **1,613건(39%)은 배당요구가 확인된 바로 그 사람의
다른 정보출처 행**이다. 행 단위로 false를 새기면 이 1,613건이 모순 데이터가 된다.

**3) 소급 복구 경로가 없다.** 마이그레이션 005는 `demanded_distribution BOOLEAN` +
`demanded_distribution_date DATE` 두 칸만 두고 **셀 원문을 남기지 않았다**. PDF 텍스트를 보관하는
테이블도 없다. 그래서 기존 NULL 4,108건을 (a)진짜 공란 / (b)그 출처에 칸 없음 / (c)컬럼 어긋남 /
(d)행 병합으로 사후 분리할 근거가 0이다. 재수집도 열람 창(기일 1주 전~기일) 안에서만 가능하다(§4-3).

#### 그래서 한 것 — 단정을 늘리지 않고 근거만 늘린다

- **파서 버그 수정**: `_parse_demanded`가 `"없" not in text`였다. `_UNKNOWN_VALUES` 검사가
  `_parse_date`에만 있고 여기엔 없어서 **"미상"·"불명"·"-"가 True(배당요구 했음)로 기록**됐다.
  개발 DB에 날짜 없는 true 3행이 그 흔적이다. 이제 날짜가 잡히면 True, "없"이 있으면 False,
  그 밖의 텍스트는 None이다. False 경로는 설계상 있었지만 단정 테스트가 없어 회귀를 못 잡았다 —
  테스트를 추가했다.
- **마이그레이션 016**: `auction_item_notice_tenant.demanded_distribution_raw TEXT`(셀 원문)와
  `auction_item_notice.tenant_table_continued BOOLEAN`(표가 다음 쪽으로 이어졌는지)을 추가했다.
  `continued`는 파서가 이미 계산했는데 저장하지 않아서 "권리신고 행이 없다"와 "2쪽에 있어 못
  받았다"를 구분할 수 없었다.
- **backfill 없음.** 016은 컬럼만 추가하고 UPDATE가 없다. 신규분과 옛 행의 구분은 컷오프로
  한다 — 점유자 행은 스캔마다 DELETE+INSERT되므로 `tenant_scanned_at`이 016 배포 시각 이후인
  명세서에서만 "raw가 NULL이면 셀이 진짜 비었다"로 읽는다(014의 컷오프 관례와 같은 형식).

#### H3와의 관계

`tools/backtest/backtest_report.sql`에 `demanded_distribution` 문자열이 없다 — H3 채점은 이
필드를 쓰지 않으므로 §4-23의 판독 불가와 **직접적 인과는 없다**. 다만 둘 다 "표를 못 읽었다와
값이 없다를 구분하지 못한다"는 같은 계열의 결함이다.

### §4-27. 동일인이 두 명으로 갈려 인수액과 임차인 수가 부풀려진다 (2026-08-11 확인)

| 2 | 권리신고 | 605호 | 160,000,000 | 2021-06-28 | `ASSUMED_FULL` 160,000,000 |

**규모**: 같은 명세서에서 `(보증금, 전입일)`이 원·일 단위까지 동일한데 `tenant_seq`가 갈린
그룹이 1,029개(2개로 갈림 1,018 + 3개로 갈림 11)이고 유령 인원이 **1,040명**, 영향 명세서가
**956건**이다 — 임차인 행이 있는 2,504건의 38%다.

**아직 고치지 않았다 — 방향에 트레이드오프가 있다.** `(보증금, 전입일)`이 같으면 동일인으로
병합하면 이 오판은 사라지지만, 다가구에서 보증금과 전입일이 우연히 같은 **별개 세입자**를
합치면 인수액을 절반으로 과소 표시하게 된다(사용자 손해 방향이 반대로 뒤집힌다). 어느 쪽 위험을
받아들일지가 결정 사항이라 사용자 판단을 받고 진행한다.

`tenantCount`(목록 카드의 "점유자 N명")도 `count(DISTINCT tenant_seq)`이라 같이 부풀려져 있다 —
고칠 때 두 경로를 함께 봐야 한다.

### §4-28. 4일 수집 공백과 커버리지 구멍 실측 (2026-08-18)

**공백**: 2026-08-14 15:08 마지막 성공 이후 2026-08-18 09:17까지 4일간 한 번도 돌지 않았다.
원인은 두 가지고 크기가 다르다.

| 원인 | 무엇이 일어났나 | 크기 |
|---|---|---|
| PC 절전 + `StartWhenAvailable: False` | 절전 중에는 3시간 트리거가 뜨지 않고, 깨어나도 놓친 회차를 보충하지 않는다 | 4일 전체 |
| `DisallowStartIfOnBatteries: True` | 절전 복귀 직후 배터리로 평가되어 08-18 09:05 회차가 거부됨(`0x800710E0`) | 1회차 |

**영향은 0이다.** 08-15(광복절·토)·08-16(일)·08-17(대체공휴일)에 매각기일이 잡힌 물건이
한 건도 없어, 공백 구간 안에서 닫힌 열람 창이 없다. 따라잡기 실행 실측: 신규 물건 713건 인입,
명세서 712건 추가, 그 712건은 전부 임차인 스캔까지 완료, `stage_failures=0`.

`0x800710E0`은 배터리 거부 외에 **이미 실행 중일 때 새 인스턴스를 무시하는 경우**
(`MultipleInstances: IgnoreNew`)에도 나온다 — 08-18 12:00 회차가 그 경우다. 코드만 보고
배터리로 단정하면 안 된다.

**조치**: 작업 조건을 `DisallowStartIfOnBatteries`·`StopIfGoingOnBatteries` False,
`StartWhenAvailable` True로 바꿨다. 그리고 `run_daily.cmd`에 이름 해석 대기를 넣었다 —
부팅 직후에는 DB가 떠도 DNS가 아직이라 5개 법원이 전부 `getaddrinfo failed`로 실패한다
(08-13 12:02 실측: stage_failures=5, 실패 요청 136건을 법원 서버에 보냄 — D-007 위반 방향).

### §4-29. 어긋난 셀을 금액 하나로 읽어 명세서를 잃고 보증금을 부풀렸다 (2026-08-18)

수집 로그의 `notice_upsert_failed ... error=bigint out of range`를 따라간 결과다. 증상이 둘이다.

- **명세서 통째 소실**: `2025타경12316` 물건1(서울남부)이 보증금 24자리를 만들어 bigint를 넘겼다.
  건별 savepoint가 그 명세서만 되돌리므로 기재사항까지 전부 저장되지 않았다. 명세서는 기일이
  지나면 다시 못 받으므로(§4-3) 한 셀 때문에 문서가 영구 소실되는 경로였다.
- **DB 오염 19행**: 15~18자리 보증금이 이미 들어가 있다. 최대 `300000000269550000`
  (3억 + 2억6,955만이 붙은 것). 이 값이 화면의 인수 보증금으로 그대로 나온다.

#### 원인 1 — 콤마 위치를 보지 않았다 (고쳤다)

`_DIGIT_AMOUNT_PATTERN`이 `^[0-9][0-9,]*$`여서 셀 안에서 줄바꿈된 금액 둘이 구분자 없이
붙은 문자열(`220,000,000231,000,000`, 실측 2025타경51589)을 18자리 수 하나로 읽었다. 콤마가
천단위로 끊겨 있을 때만 금액 하나로 읽게 하고, 어긋나면 기존 다중 금액 경로(순번형=뒤,
그 외=앞)로 보낸다. 콤마가 아예 없는 이어붙음(`4000000040000000`)은 그 규칙으로 못 걸러
상한 1조로 막고 버린다 — 실측 최대 보증금이 20억(2025타경597)이라 현실값과 겹치지 않는다.
`2025타경12316`은 이 수정으로 저장됐다(보증금 40,000,000 / 차임 1,500,000 2행).

#### 원인 2 — 앵커 없는 행이 이웃 행에 삼켜진다 (아직 고치지 않았다)

`2025타경12316`은 임차인 2명 × 정보출처 2행 = **4행**인데 2행으로 뭉쳤다. 현황조사 행은
전입신고일자·배당요구여부 칸이 비어 있어 `_ANCHOR_FIELDS` 기준으로 **앵커가 없다**. 그러면
`_rows_in_region`의 밴드(행 중앙 기준 대칭)가 아래 임차인의 현황조사 행까지 삼킨다.

| y(중앙) | 내용 | 실제 소속 | 현행 귀속 |
|---|---|---|---|
| 463.5 | 현황조사 40,000,000 1,500,000 | 임차인A 현황조사 | 행1 |
| 431 | 권리신고 … 2015.11.6. 2025.11.3. | 임차인A 권리신고 (앵커) | 행1 |
| 398 | 현황조사 40,000,000 1,500,000 | **임차인B 현황조사** | 행1 |
| 364 | 권리신고 … 2015.11.5. 2025.12.8. | 임차인B 권리신고 (앵커) | 행2 |

행1의 밴드가 (382, 480]으로 계산돼(2×431−480=382) 398이 들어간다. 그래서 정보출처가
`현황조사권리신고현황조사`, 점유부분이 `406호중일부406호406호중일부`가 됐다.

**규모**: 정보출처에 값이 두 개 이상 들어간 행이 **54행/54건**이다
(`등기사항전부증명서현황조사` 24 / `등기사항전부증명서권리신고` 9 / `현황조사권리신고` 8 /
`현황조사현황조사` 5 / `현황조사등` 4 / `등기사항전부증명서등기사항전부증명서` 2 / 그 밖 2).

**후보 수정을 실험했지만 채택하지 않았다.** 정보출처를 앵커 컬럼에 추가하면(모든 행에 값이
하나씩 있으므로) 12316은 4행으로 정확히 갈린다. 픽스처 11종 중 10종은 결과가 같고 9542는
성명이 다음 행으로 옮겨간다. 문제는 **성명 병합셀 귀속**이다 — 성명은 rowspan 병합셀에
한 번만 렌더되고 병합 구간의 세로 중앙에 놓이므로, 행이 잘게 갈리면 성명이 그 사람의
두 번째 행에 떨어진다. 그러면 첫 번째 행은 성명이 없어 `_to_tenants`가 **직전 사람의 연속**으로
붙인다(실험 결과: 임차인B의 현황조사 행이 임차인A의 순번으로 귀속). 병합셀 경계는 표 괘선이라
텍스트 레이어에 없어 좌표만으로는 복원할 수 없다.

즉 이 수정은 §4-27(동일인이 두 seq로 갈리는 문제)과 같은 결정을 필요로 한다 — 행·사람 묶기
기준을 무엇으로 둘지. 둘을 함께 결정한다.

#### 오염 행 정리 — 단계적 재수집 (2026-08-18 시작)

오염은 **19행/18건**이었다. 열람 창(기일 1주 전~기일)이 열린 것만 그때그때 다시 받는다.
`tenant_scanned_at`을 비우면 daily가 다시 열고, 저장 시 그 명세서의 점유자 행을
DELETE+INSERT하므로 옛 행이 교체된다.

```sql
-- 창이 열린 명세서의 스캔 마커만 비운다 (그 뒤 daily 회차가 다시 읽는다)
UPDATE auction_item_notice SET tenant_scanned_at = NULL WHERE id IN (...);
```

- **완료 8건** (기일 2026-08-25, 창 08-18 개시): notice 2751·2576·3037·3045·3044·3002·2869·3012.
  마커를 비우고 같은 날 실제 수집 경로로 다시 받았다. 보증금이 정상값으로 교체됐다
  (예: `220,000,000231,000,000` → 220,000,000 / `8500000085000000` → 85,000,000).
  실측 잔여: 상한 초과 행 19 → **10**, 15자리 1 → 0, 16자리 8 → 3, 18자리 11 → 7.
- **남은 9건** — 창이 여는 날에 위 SQL을 돌린다.
  - 08-20 개시(기일 08-27): notice 3316
  - 08-24 개시(기일 08-31): notice 3691·3723
  - 08-25 개시(기일 09-01): notice 3835·3844·4015·4030·4079·3559
- **회수 불가 1건**: notice 2268 (`2025타경11598` 물건1, 기일 2026-08-12 경과). 보증금이
  `150000000150000000`으로 남아 있다 — 재수집 경로가 없어 값을 비우는 것 외에 방법이 없다.

### §4-30. 행·사람 묶기 방향 확정 — 괘선 없이는 못 푼다 (2026-08-20)

§4-27(동일인이 두 seq로 갈림)과 §4-29(행 뭉침)를 함께 결정하기로 한 건이다. 세 방식을
실측 비교했고, **좌표만으로 푸는 길은 기각**, **PDF 괘선을 읽는 길로 간다**로 정했다.

#### 실측 규모 (2026-08-20 기준, §4-27의 08-11 수치 갱신)

`(보증금, 전입일)`이 완전히 같은데 seq가 갈린 그룹 **1,520** / 유령 인원 **1,533** /
영향 명세서 **1,420건** — 임차인 행이 있는 3,477건의 **41%**다.

반대 방향(과소 표시)도 새로 실측했다: 한 seq 안에 전입일도 보증금도 서로 다른 행이 섞인 경우가
**169 seq / 131 명세서**다. 다른 사람을 한 명으로 세고 있다는 뜻이고, §4-27에 기록되지 않은
방향이다. 즉 현행은 **양방향으로 틀린다**.

#### §4-27의 진단을 정정한다

§4-27은 원인을 "정보출처마다 성명 표기가 다르다"로 적었다. 실제로는 **성명 셀이 여러 줄로
감싸이는데 그 줄들이 서로 다른 행으로 흩어져 각각 부분 문자열이 되는 것**이다.
실측: DB의 `주식회`는 별개 표기가 아니라 `에이파이낸셜대부주식회사`가 잘린 것이다
(픽스처 2593_1에서 같은 문자열이 5줄로 렌더되는 것을 확인).

#### 기각 — 성명 병합셀 중심으로 span을 역산하는 방안

성명 병합셀은 걸친 행들의 세로 중앙에 렌더되므로, 정보출처를 행 앵커로 쓰고 성명 중심에서
행 구간을 DP로 역산하면 풀릴 것으로 보였다. 픽스처 7종 중 5종이 오차 0.5pt 이하로 맞는다.

**그런데 어려운 문서에서 새 오류를 만든다.** 908_1의 마지막 두 행은 보증금 10,000,000 /
15,000,000, 전입일 2021-08-20 / 2021-06-22로 **별개 임차인 둘**인데(DB notice 128에서 확인),
이 방식은 한 사람으로 합친다. 성명 줄바꿈 간격(12.5~13pt)과 인접 행의 성명 줄 간격이
구분되지 않기 때문이다. 중심 위치로 가설을 검정하면 두 이름(오차 6.00/6.25pt)이
한 이름(오차 9.50pt)보다 잘 맞지만, **이 정도 차이를 판정 기준으로 삼을 수는 없다.**

쉬운 문서는 현행 파서도 이미 맞히므로 실익이 없고, 어려운 문서에서만 틀린다. 채택하지 않는다.
§4-29가 "좌표만으로는 복원할 수 없다"고 쓴 것이 옳았다.

`GET https://pvo.scourt.go.kr/streamdocs/v4/documents/{streamdocsId}`에
`Authorization: Access-Token {accessToken}`을 붙이면 **PDF 원본**이 온다
(`%PDF-1.4`, 92,811바이트). 수집기는 이미 `open_document`으로 그 세션을 만들고 있으므로
**명세서당 요청 1회**만 늘어난다. 우회가 아니다 — 접미사 없는 문서 엔드포인트 그대로다.

파서 후보는 `opendataloader-pdf`(Apache-2.0, 괘선 border analysis + 텍스트 클러스터링)다.
검증 결과:

| 검증 | 결과 |
|---|---|
| 병합셀 구분 (합성 PDF) | **통과** — `row span=2`로 병합 행을, 이웃 짧은 이름 둘을 별개로 |
| JSON 기계 판독 | 셀마다 `row number`·`column number`·`row span`·`column span`·`bounding box` |
| 실제 한국 공문서 (등기부) | 병합셀·한글 정상. 다만 **표를 과분할**한다(29개 중 8개는 셀 안에 중첩) |
| 워터마크 오염 | 등기부는 `열/람/용`이 셀에 침투. **명세서는 해당 없음** — 텍스트 레이어 11종 전부 0건 |

이 방식이 근본 해법인 이유는 **임차인의 정체를 문자열이 아니라 병합셀로 정의**할 수 있어서다.
`tenant_seq = 성명 컬럼 셀의 (row number, row span)`. 성명이 잘리든 여러 줄로 감싸이든 무관해진다.

**미확인**: 실제 명세서에서 점유자 표가 하나로 잡히는지(과분할 위험). 실문서 1건으로 확인해야 한다.
**제약**: Java 11+ 런타임이 필요하다. 이 PC는 JDK 21이 깔려 있는데도 `java`가 8로 잡히므로
(`C:\Windows\System32\java.exe`) 도입 시 `run_daily.cmd`에 경로를 명시해야 한다.

#### 폴백 설계

괘선을 얻은 문서는 괘선 기준, 못 얻은 문서는 현행 좌표 기준으로 파싱하고 **어느 경로였는지
기록**한다. 그래야 나중에 품질을 갈라서 볼 수 있다. 열람 창이 닫힌 과거 문서는 현행 결과가 그대로 남는다.

### §4-31. 명세서 PDF 취득 경로 — 저장 흐름 해부 (2026-08-20)

§4-30에서 "PDF 괘선으로 간다"고 정했다. 실제 취득 경로를 뜯어본 결과를 남긴다.
**실제 명세서로 검증까지 끝냈다** — 아래 §4-32.

#### 뷰어의 저장 버튼은 2단계다

브라우저 DevTools로 실제 요청을 확인했다(사용자 캡처, 2026-08-20).

```
1) POST https://pvo.scourt.go.kr/streamdocs/v4/documents/{원본id}/changes
   Authorization: Access-Token {accessToken}
   Cookie: accessToken=...; WMONID=...; JSESSIONID=...
   body: {"layout":[],"annot":[],"acroform":[],"acroformProp":{"CO":[]},
          "watermark":[...],"outline":[],"saveAsIncremental":true}
   →  {"streamdocsId":"{새 id}"}

2) GET  https://pvo.scourt.go.kr/streamdocs/v4/documents/{새 id}
        ?Y2NkN2E5={서명 토큰}&originalId={원본id}&fileName={...}.pdf
   →  PDF
```

- **핵심**: 다운로드는 **원본 id가 아니라 `/changes`가 돌려준 새 id**로 받는다. 사본을 먼저
  만드는 것이 정상 절차다. 우리가 원본 id를 직접 GET하던 것이 잘못이었다.
- 2단계는 **iframe 이동**이다(`Sec-Fetch-Dest: iframe`, `Sec-Fetch-Mode: navigate`).
  주소 이동에는 `Authorization` 헤더를 붙일 수 없어 토큰을 쿼리로 싣는다.
- 쿼리 파라미터 이름 `Y2NkN2E5`는 base64로 `ccd7a9`다.
- `POST /streamdocs/v4/collects/put`도 같이 나가는데 **사용 통계**라 무관하다.
- 워터마크는 `renderTarget: SCREEN`(화면 전용)이라 저장본에는 들어가지 않는다.
  실제로 내려받은 PDF의 텍스트 레이어에 워터마크 문구가 0건이다.

#### 프로그램으로 어디까지 됐나 (실측)

| 단계 | 결과 |
|---|---|
| 세션 열기(`open_document`) | 성공 |
| `POST /changes` (워터마크 없는 사본) | **성공** — 새 id 반환 |
| `GET /documents/{새 id}` + Authorization 헤더 | **403** |
| 〃 + `Cookie: accessToken=...` 추가 | **403** |

즉 남은 것은 **쿼리 토큰 `Y2NkN2E5` 하나**다. 이 값은 뷰어의 자바스크립트가 만든다.

#### A(직접 요청) 완성 — 토큰 재현 (2026-08-20)

뷰어 번들 `chunk-NQ3JAQ6X.js`에서 토큰 생성 로직을 읽어 재현했다.

```
token = base64( SHA-512( 분단위내림_epoch_ms_문자열 + docId ) XOR 하드코딩_64바이트_키 )
```

- `docId`는 **`/changes`가 돌려준 새 id**다(원본 id가 아니다).
- 시각은 `Date.now()+오프셋`을 분 격자로 내린 값이다 — 토큰은 **1분마다 바뀐다**.
- 쿼리 **파라미터 이름은 난수**다(`btoa(랜덤 16진수 6자)`). 서버는 이름을 보지 않는다.
- 구현·검증: `src/collector/streamdocs_token.py`, `tests/test_streamdocs_token.py`.

**오프라인 검증**: 브라우저에서 실제로 나간 URL의 토큰값과, 같은 docId·같은 분으로 계산한 값이
바이트 단위로 일치했다(일치 시각 epoch `1787203680000` = 2026-08-20 14:28 KST). 법원에 요청을
보내지 않고 알고리즘의 정확성을 확인한 것이다.

**실취득 성공**: 요청 2회(`/changes` + 다운로드)로 PDF 94,881바이트를 받았다. opendataloader로
파싱한 결과가 브라우저 저장본과 동일하다(14행×17열, 임차인 2명 정확히 분리). 브라우저 저장본은
403,302바이트인데 차이는 도장 이미지뿐이고 표 구조는 같다.

**성격에 대한 기록**: 이 토큰은 `"crypto"`·`"sha-512"` 같은 평범한 문자열까지 문자코드 배열로
숨기고 하드코딩 키로 XOR을 덧씌운 **자동화 방지 장치**다(변수명 `noBypass`). 열람 권한 자체는
이미 허가된 세션으로 통과하고 있으므로 권한을 뚫는 것은 아니지만, 운영자가 프로그램 접근을
막으려 둔 장치인 것은 분명하다. **사용자 결정으로 진행했다**(2026-08-20).
D-007의 선은 그대로다 — **차단이 감지되면 우회하지 않고 중단·알림**한다.

이득: 건당 요청 2회로 끝나 브라우저(B안)보다 훨씬 가볍다.

## §5. 알려진 한계

- 응찰자수·낙찰자 확보 불가(§1-1) → 경쟁 강도를 지표로 쓸 수 없다.
- 과거 소급 불가(§1-4) → 표본이 시간에 비례해서만 늘어난다. 초기 통계는 신뢰구간이 넓다.
- 공매 미포함(§1-5) → LH가 공매로 매입한 건은 관측되지 않는다.
- 시세 데이터 없음 → H4는 로드맵 2-3(실거래가 API) 이후에만 가능.
- 등기부는 CODEF 유료 호출 → H2·H5·H6은 표본 전수가 아니라 표본 추출로 해야 비용이 감당된다.
  (단 매각물건명세서로 상당 부분 대체 가능한지 확인 중 — 확인되면 이 한계가 크게 완화된다)
- **과거 유찰 이력 전체는 백필 불가**. 사건검색은 현재 공고분 위주로 기일을 돌려준다
  (`2023타경4722`는 19차 기일 중 2행만). 유찰 횟수는 `auction_item.failed_bid_count`(수집 시점
  스냅샷)에 의존해야 하고, 기일별 최저가 추이는 앞으로 쌓아야 한다.
- `CASE_SEARCH` 출처 행은 `failed_bid_count`가 NULL이다(사건검색이 제공하지 않음).
