# 권리분석 화면 UX 재설계 — "무슨 말인지 모르겠다"를 고친다

작성일 2026-08-21. 대상: `apps/web/app/items/components/RightsAnalysisView.tsx`(지도 패널·상세 페이지 공유, 본문 폭 최소 350px).
계기: 사용자 피드백 두 건 — "무슨 말을 하려는 건지 모르겠다", "권리분석탭 자체 내용이 너무 길다".
전제: 매각물건명세서 데이터(`notice-analysis.ts`) + 물건별로 받은 경우에만 등기부(`registry.ts`) + 실부담 시나리오(`affordability.ts`). 이 문서는 설계만 다루고 구현 순서는 §6에 있다.

제약(요약): 판단·권유 문구 금지(D-011, 변호사법 §109 — 사실 서술과 규칙 ID만), 빈 값이 "문제 없음"으로 읽히면 안 됨, 해요체·전문용어 쉬운 설명 병기(UX-03·T-09~13), 스타일 값은 `packages/design-tokens` 토큰 참조만.

## 1. 문제 진단 — 왜 "무슨 말인지 모르겠다"가 나오나

현재 `RightsAnalysisView.tsx`가 그리는 블록을 위에서부터 세면 **13개**다 (괄호는 현재 코드 위치).

1. 등기부 미연동 고지 (L271)
2. 명세서 원문 보기 버튼 (L276)
3. 요약 카드 "매수인이 인수하는 보증금" (L282)
4. 조건부 각주 2종 (L301, L307)
5. 체크리스트 4항목 "이것부터 확인해요" (L314)
6. 등기부 블록 (L316)
7. 규칙표 "이 금액에 무엇이 들어갔나" (L318)
8. 시나리오 "결국 얼마가 드나" (L320)
9. 한눈 요약 바 3칩 (L322)
10. "최선순위 설정" (L337)
11. "명세서 기재사항" (L357)
12. 임차인별 상세 (L374)
13. 면책 (L387)

이 구조에서 다음 네 가지가 "모르겠다"를 만든다.

### 진단 ① 화면이 대답이 아니라 **한계 고지로 시작한다**

사용자가 처음 읽는 문장이 "매각물건명세서로만 계산했어요. 등기부는 아직 연동하지 않아서 등기 권리와 채권액은 빠져 있어요"다. 첫 문장 안에 처음 보는 용어가 셋(매각물건명세서·등기부·채권액)이고, 정작 사용자의 질문("이 집 사면 나한테 무슨 일이 생기나")에는 세 블록 뒤에야, 그것도 문장이 아니라 숫자로만 답한다.

### 진단 ② 헤드라인이 **숫자일 뿐, 문장이 아니다**

"매수인이 인수하는 보증금 — 6,500만 원". 인수를 모르는 사람에게 이 숫자는 잔액처럼 보일 뿐, **"낙찰가에 이 돈을 더 얹어 계산해야 한다"는 결과**가 어디에도 문장으로 적혀 있지 않다. "매수인"이 자기 자신을 가리킨다는 것조차 도메인 지식이다. 화면 전체에서 가장 크게 보이는 값이 해석 불가능하면, 나머지를 다 읽어도 회복되지 않는다.

### 진단 ③ 같은 사실이 **2~3번 다른 옷을 입고 반복**되어 길이가 늘고 서사가 끊긴다

- 말소기준: 체크리스트 ①(L314) ↔ "최선순위 설정" 섹션(L337) — `baselineRaw` 동일 값 2회.
- 임차인 수·인수 여부: 체크리스트 ②④ ↔ 한눈 요약 바(L322) ↔ 임차인별 상세(L374) — 3회.
- 인수되는 권리: 체크리스트 ③ ↔ "명세서 기재사항"(L357) — 2회.
- 인수 금액의 의미: 요약 카드 ↔ 규칙표의 임차인 행(L106) — 2회.

정보가 반복되면 사용자는 "아까 그 얘기랑 뭐가 다르지?"를 매번 판정해야 한다. 이게 "너무 길다"와 "무슨 말인지 모르겠다"의 공통 원인이다 — 화면에 이야기가 하나가 아니라, 부분 이야기 여러 개가 이어 붙어 있다.

### 진단 ④ 상태 어휘가 **세 벌**이고 용어가 설명보다 먼저 나온다

- 체크리스트: 확인됨 / 확인 필요 / 알 수 없음 (`CHECKLIST_STATUS_LABEL`)
- 임차인 배지: 인수 안 함 / 보증금 전액 인수 / 인수 금액 확인 필요 / 판정 불가 (`NOTICE_ASSUMPTION_LABEL`)
- 규칙표 배지: 인수 / 인수 안 함 / 확인 필요 (`BURDEN_STATUS_LABEL`)

"확인 필요"가 섹션마다 다른 뜻으로 쓰인다. 또 대항력·말소기준·배당요구·배당요구종기·최선순위 설정·명도·일괄매각이 본문에 먼저 등장하고 설명이 뒤따르거나 아예 없다. 규칙표(L318)는 "근저당·저당권, 압류·가압류, 담보가등기, 경매개시결정"처럼 용어 6개를 한 줄에 쏟는데, 이 표는 **이 물건에 대한 정보가 아니라 일반 규칙**이라 초심자의 질문 순서와도 어긋난다.

## 2. 이 화면이 답해야 할 질문 (도메인 지식 없는 사람 기준)

1. **이 집을 낙찰받으면, 낙찰가 말고 더 물어줘야 할 돈이 있나? 얼마인가? 혹은 아직 알 수 없나?**
2. **지금 이 집에 누가 살고 있나? 낙찰받으면 그 사람과 나 사이에 무슨 일이 남나?**
3. **집에 걸려 있는 빚(근저당 같은 것)은 내가 떠안나?**
4. **다 합치면 이 집을 갖는 데 총 얼마가 드나?**
5. **이 화면이 말해주지 못하는 것은 무엇이고, 내가 직접 확인해야 하는 것은 무엇인가?**

현재 화면은 1~4의 재료를 모두 갖고 있지만 질문 순서로 배열되어 있지 않고, 5는 각 섹션의 각주·limit 문장에 흩어져 있다. 재설계는 **이 다섯 질문을 화면 구조 그 자체로 만든다.**

## 3. 개선안

### 3-1. 정보 구조 — 13블록 → "결론 1 + 질문 3 + 확인 목록 1"

```
[근거 줄]   한 줄: 무엇으로 계산했는지 + 원문 링크        (항상 표시)
[결론 카드] 큰 값 + 결론 문장 1~2개                        (항상 표시)
[섹션 1]    지금 살고 있는 사람        요약 문장 → ▸ 상세 접힘
[섹션 2]    집에 걸려 있는 빚과 권리    요약 문장 → ▸ 상세 접힘
[섹션 3]    결국 얼마가 드나           대표 1줄 → ▸ 상세 접힘
[확인 목록] 직접 확인할 것 — 흩어진 limit들을 한 곳에      (항상 표시)
[면책]      한 줄                                          (항상 표시)
```

- **접힘의 원칙**: 각 섹션의 **요약 문장은 항상 보인다.** 접히는 것은 근거 행(임차인별 상세, 권리 종류별 규칙, 시나리오 나머지)뿐이다. 미확정·인수 가능 사실은 전부 요약 문장에 올라오므로, 접혀 있어도 "빈 값 = 문제 없음" 오독이 생기지 않는다.
- 접힘 UI는 `docs/design/design-adaptation.md` §3의 기존 매핑(`faq-accordion-item`)을 그대로 쓴다. 새 시각 언어를 만들지 않는다.
- 지도 패널(350px)과 상세 페이지가 같은 컴포넌트를 계속 공유한다. 기본 접힘 상태도 동일하게 둔다 — 두 화면이 다른 말을 하면 안 된다는 기존 원칙(파일 상단 주석) 유지.
- `rights-checklist.ts`의 판정 로직(status·facts·limit)은 **그대로 데이터 엔진으로 남긴다.** 바뀌는 것은 렌더링이다: ②(대항력)·④(점유)가 섹션 1로, ①(말소기준)·③(인수권리)이 섹션 2로 들어가고, 각 항목의 `limit`은 [확인 목록]으로 모인다. "기준선 → 앞선 임차인 → 남는 권리 → 명도"라는 확인 순서 교육은 섹션 1·2의 요약 문장 안에서 유지된다.

### 3-2. 판단 금지(D-011) 안에서 "그래서 뭐?"에 답하는 방법

판단("이 물건은 안전/위험")은 못 하지만, 다음 세 가지는 전부 **사실 서술**이라 할 수 있다. 이 셋이 "그래서 뭐?"의 답이다.

1. **법적 효과를 지갑 단위로 번역한다.** "보증금 전액 인수" → "낙찰가와 별도로 이 보증금을 매수인이 세입자에게 돌려줘야 해요". 인수라는 법률 효과의 내용을 그대로 풀어 쓴 것이지 평가가 아니다.
2. **불확실성의 방향을 명시한다.** "확인 필요" → "0원이라는 뜻이 아니에요 / 실제 금액은 이보다 클 수 있어요". 하한·상한이라는 사실을 적는다.
3. **다음 절차를 사실로 제시한다.** "등기부의 빚 목록이 있어야 금액이 확정돼요"는 계산의 전제 조건이라는 사실이다. 기존 면책 문구("입찰 전 등기사항전부증명서를 꼭 확인해주세요")가 이미 쓰는 방식이며, 입찰 여부에 대한 권유가 아니다.

금칙어(자동 검사 대상, §6): 추천·안전·위험·괜찮·유리·불리·조심·주의하세요. 규칙 출처 표기는 현행대로 유지한다(예: `RIGHT_CLASSIFICATION v1`).

### 3-3. 실제 문구 — 화면에 그대로 들어갈 한국어

용어는 **처음 등장하는 자리에서 한 번 괄호 병기**하고, 그 뒤로는 그냥 쓴다. 병기 문구는 상수로 한 곳(`notice-labels.ts`)에 둔다.

| 용어 | 병기 문구 (첫 등장 시) |
|---|---|
| 인수 | 인수(낙찰받은 사람이 떠안는 것) |
| 소멸 | 소멸(낙찰과 동시에 지워지는 것) |
| 대항력 | 대항력(보증금을 돌려받을 때까지 집을 비워주지 않아도 되는 힘) |
| 말소기준 | 말소기준(권리가 남는지 지워지는지 가르는 기준 날짜) |
| 배당요구 | 배당요구(법원에 "내 보증금을 낙찰대금에서 돌려달라"고 신청하는 것) |
| 배당요구종기 | 배당요구 마감일 |
| 명도 | 명도(살고 있는 사람에게서 집을 넘겨받는 일) |
| 매각물건명세서 | 매각물건명세서(법원이 이 물건에 대해 공식으로 알리는 문서) |
| 매수인 | 매수인(낙찰받은 사람) |
| 감정가 | 감정가(법원이 감정평가로 매긴 값 — 시세와 달라요) |

**근거 줄** (현재 L271 고지 3줄 → 1줄로 축소, 전체 설명은 화면 맨 아래 접힘으로 이동):

> 근거: 매각물건명세서 · 등기부 미확인 — [원문 보기]
> (등기부를 받은 물건이면) 근거: 매각물건명세서 · 8.13 열람 등기부 — [원문 보기]

**결론 카드** — 헤드라인 케이스별(`assumedHeadline`의 AMOUNT / UNCONFIRMED / NONE과 1:1). 라벨과 문장이 함께 간다. 조건 문장은 숫자와 **같은 카드 안**에 둔다 — 각주로 떨어뜨리면 숫자만 읽고 지나간다.

- `AMOUNT` (확정 금액):
  > **낙찰가와 별도로 돌려줘야 하는 보증금**
  > **6,500만 원**
  > 먼저 살던 세입자의 보증금이에요. 낙찰받으면 낙찰가와 별도로 매수인(낙찰받은 사람)이 세입자에게 돌려줘야 해요. 법원 문서에는 "인수"라고 적혀 있어요.
- `AMOUNT` + `isLowerBound`: 위 문장 + 
  > 금액이 확정되지 않은 세입자가 더 있어, 실제로는 이 금액보다 클 수 있어요.
- `UNCONFIRMED` (금액 산출 불가 — 큰 숫자 자리에 금액 대신 텍스트):
  > **낙찰가와 별도로 돌려줘야 하는 보증금**
  > **아직 계산할 수 없어요**
  > 돌려줘야 할 수 있는 보증금이 있어요. 0원이라는 뜻이 아니에요 — 세입자가 배당(낙찰대금을 나눠주는 절차)에서 얼마를 돌려받는지는 등기부의 빚 목록이 있어야 계산할 수 있어요.
- `NONE` (0원이 사실인 경우):
  > **낙찰가와 별도로 돌려줘야 하는 보증금**
  > **0원 — 명세서 기준**
  > 명세서에서는 떠안는 보증금이 확인되지 않았어요. 다만 이 계산은 법원 명세서만 본 결과라, 등기부의 권리까지 확인한 것은 아니에요.
- `analysis === null` (명세서 미수신): 현행 문구 유지 — 이미 잘 쓰여 있다.

**섹션 1 — 지금 살고 있는 사람** (체크리스트 ②④ + 임차인 상세 + 한눈 요약 바를 흡수):

요약 문장(대표 케이스):
- 대항력 있는 임차인 존재:
  > 세입자 2명이 살고 있어요. 그중 1명은 기준 날짜보다 먼저 전입해서, 보증금을 돌려받을 때까지 집을 비워주지 않아도 돼요. 이런 힘을 대항력이라고 해요.
- 전원 기준일 이후:
  > 세입자 1명이 살고 있어요. 기준 날짜보다 늦게 전입해서, 보증금은 낙찰대금에서 해결되고 매수인이 떠안지 않아요. 다만 집을 비우는 일(명도)은 낙찰 후에 남아요.
- `noTenantRecorded === true`:
  > 법원 조사에서 세입자가 확인되지 않았어요. 빈집이라는 뜻은 아니에요 — 누가 살고 있는지는 현장에서만 알 수 있어요.
- 점유자 표를 못 읽음(`noTenantRecorded === null` && 임차인 0명):
  > 세입자 정보를 읽지 못했어요. 없다는 뜻이 아니에요.

▸ 접힌 상세: 현행 `TenantRow`를 유지하되 판정 사유(`NOTICE_ASSUMPTION_REASON`)를 풀어 쓴다.

| 판정 | 현행 사유 문구 | 개선 문구 |
|---|---|---|
| NOT_ASSUMED | 대항력이 말소기준보다 늦어요 | 기준 날짜보다 늦게 전입해서, 보증금을 매수인이 떠안지 않아요 |
| ASSUMED_FULL | 대항력이 있는데 배당요구가 없거나 종기를 넘겼어요 | 기준 날짜보다 먼저 전입했는데 배당요구를 하지 않았어요(또는 마감일을 넘겼어요). 그래서 보증금 전액이 매수인에게 넘어와요 |
| ASSUMED_AMOUNT_UNKNOWN | 대항력과 배당요구가 모두 있어요. 배당으로 얼마를 회수할지는 등기부가 있어야 알 수 있어요 | 먼저 전입했고 배당요구도 했어요. 배당에서 못 돌려받는 만큼을 매수인이 내주는데, 그 금액은 등기부의 빚 목록이 있어야 계산돼요 |
| UNKNOWN | 전입일이나 최선순위 설정일이 명세서에 없어요 | 전입일이나 기준 날짜가 명세서에 없어 판정할 수 없어요 |

**섹션 2 — 집에 걸려 있는 빚과 권리** (체크리스트 ①③ + "최선순위 설정" + 규칙표 + "명세서 기재사항" + 등기부 블록을 흡수):

요약 문장(요소를 조건부로 이어 붙인다 — 데이터는 전부 `notice-analysis.ts`·`registry.ts`에 있는 것만):
- 기준선 (`baselineDate` 있음):
  > 2019.3.4에 설정된 권리(근저당)가 기준이에요 — 이것이 말소기준이에요.
- 규칙 한 줄 (항상):
  > 은행 빚(근저당)·압류·가압류는 낙찰되면 지워져요. 매수인이 대신 갚지 않아요.
- 인수권리 (`assumedRightsKind`별):
  - `LEASEHOLD_REGISTRATION` 등: `다만 법원이 "주택임차권등기는 매수인이 인수한다"고 적었어요.`
  - `NONE`: `법원은 인수되는 권리를 "해당사항없음"으로 적었어요.`
  - 란이 비어 있음: `명세서의 인수권리 란이 비어 있어요 — 없다는 뜻인지 확인이 필요해요.`
- 등기부 상태 (`registry.status`별):
  - `FETCHED`: `8.13에 받은 등기부에는 근저당 2건, 가압류 1건이 있어요.` (금액이 있으면 합계 병기)
  - `NOT_FETCHED`: `이 집 등기부는 아직 받지 않았어요. 받으면 실제로 걸려 있는 권리를 볼 수 있어요.`
- `baselineDate === null`: `명세서에 기준 날짜가 적혀 있지 않아, 어느 권리가 지워지는지 판정할 수 없어요.`

▸ 접힌 상세: 권리 종류별 규칙 2행(현 `REGISTERED_BURDEN_RULES` — 문구 유지, `REGISTERED_BURDEN_NOTE`의 규칙 ID 표기 유지), 명세서 특이사항(`riskFlags` 라벨), 등기부 표와 발급 확인 플로우(현 `RegistrySection` 그대로 — 돈이 나가는 버튼이라 접힘 속이 오히려 맞다), 배당요구 마감일.

**섹션 3 — 결국 얼마가 드나** (개념 유지, 표면만 축소):

- 요약 1줄 (기존 `summaryScenario` 선택 규칙 재사용 — 중위 우선, 없으면 최저가):
  > 유사 물건 중간 가격대(3.1억)로 낙찰되면 총 3.8~4.0억이 들어요 — 낙찰가 + 돌려줄 보증금 + 세금·비용.
- ▸ 접힌 상세: 나머지 시나리오 행 + 전제 각주(현행 문구를 문장 3개로 절단: 감정가 기준임 / 취득세는 구간임 / 체납 관리비는 합산에 없음).
- `bulkSale`·시나리오 없음 케이스는 현행 문구 유지.

**확인 목록 — 직접 확인할 것** (신규 블록, 각 섹션의 `limit`·미확정 사유를 한 곳에 모은다):

> **이 화면이 대신 못 하는 것**
> - 등기부 — 빚 목록이 있어야 돌려줄 보증금 금액이 확정돼요. (아직 확인 전)
> - 체납 관리비 — 공용부분 체납액은 매수인이 낼 수 있는데, 금액은 관리사무소만 알아요.
> - 현장 — 누가 살고 있는지는 서류만으로 알 수 없어요.

항목은 조건부다: 등기부를 받았으면 첫 항목이 빠지고, `unknownItems`가 비면 관리비 항목이 빠진다. 전부 해소되면 블록 자체를 그리지 않는다. 이 목록이 D-011 안에서 "그래서 나는 뭘 하면 되나"의 답이다 — 입찰 권유가 아니라 확인 절차의 사실.

**면책** (현행 유지, 1줄):
> 명세서에 적힌 사실을 규칙대로 정리한 참고 정보예요. 실제 입찰 전 등기사항전부증명서와 명세서 원문을 꼭 확인해주세요.

### 3-4. 상태 어휘 통일

세 벌을 두 벌로 줄인다.
- **돈 축** (임차인·권리 행 배지): `인수` / `인수 안 함` / `금액 미확정` — `ASSUMED_AMOUNT_UNKNOWN`의 현행 라벨 "인수 금액 확인 필요"를 "금액 미확정"으로 바꿔 지식 축과 분리한다.
- **지식 축** (섹션 요약·확인 목록): `확인됨` / `미확인` — "알 수 없음"·"판정 불가"·"확인 필요"를 "미확인 + 이유 문장"으로 통일한다.

배지 색 톤(`Badge` tone 매핑)은 현행 유지 — 시각 규칙은 이미 일관적이고, 문제는 어휘였다.

## 6. 구현 순서 (작은 단계 + 단계별 검증)

각 단계는 독립적으로 커밋·검증 가능하다. 공통 검증: `pnpm --filter @auction/web lint && pnpm --filter @auction/web test && pnpm --filter @auction/web build`. 새 테스트 파일은 `apps/web/package.json`의 `test` 열거와 `tsconfig.test.json`에 등록해야 실행된다 (`apps/web/CLAUDE.md`).

**0. 선행 확인** — 미커밋 트리에서 `RightsAnalysisView.tsx` L314가 `rightsChecklist(analysis, registry ?? null)`로 2인자를 넘기는데 `rights-checklist.ts`는 1인자 시그니처다. 등기부 연동 작업과 충돌하지 않게 이 정합부터 맞춘 뒤 시작한다.
   - 검증: `pnpm --filter @auction/web build` 통과.

**1. 결론 문장 생성기** — `rights-summary.ts`(신규, 순수 함수): `assumedHeadline` 케이스 + `isLowerBound` + `registry.status`를 받아 결론 카드 라벨·문장 배열을 돌려준다. §3-3 문구를 그대로 상수로.
   - 검증: 단위 테스트 — AMOUNT/AMOUNT+하한/UNCONFIRMED/NONE × 등기부 유무 케이스별 문장 스냅숏. 금칙어 테스트(모든 문구 상수에 추천·안전·위험·괜찮·유리·불리·조심 부재 단언)를 여기서 함께 만든다.

**2. 용어 병기·상태 어휘 정리** — `notice-labels.ts`: 병기 상수 추가, `NOTICE_ASSUMPTION_REASON` 4문구 교체(§3-3 표), `ASSUMED_AMOUNT_UNKNOWN` 라벨 "금액 미확정"으로 교체. 목록 카드가 쓰는 `assumedDepositCardLabel` 분기 문구도 같은 어휘로 맞춘다.
   - 검증: 기존 라벨 테스트 갱신 + 금칙어 테스트 통과. 목록·지도 카드 문구가 함께 바뀌는 것을 눈으로 확인.

**3. 결론 카드 교체 + 상단 정리** — `RightsAnalysisView.tsx`: 3줄 고지 → 1줄 근거 줄(원문 버튼 포함), `summaryCard`를 1단계 생성기로 교체, 조건부 각주 2종·`glanceBar` 삭제.
   - 검증: 빌드 + 지도 패널(350px)·상세 페이지 양쪽 수동 확인(케이스별 물건 4개: 확정금액·하한·미확정·0원). 줄바꿈 넘침 없는지 350px에서 확인.

**4. 섹션 재편 + 접힘** — 접힘 컴포넌트 1개 신설(`<details>` 기반, `faq-accordion-item` 토큰). 섹션 1·2·3으로 재배열: "최선순위 설정"·"명세서 기재사항"·`BurdenScopeSection`·`RegistrySection`·임차인 상세를 §3-1 구조로 흡수. `ChecklistSection` 렌더 제거(로직은 유지).
   - 검증: 빌드 + 두 진입점 확인. 접힘 전부 닫은 상태에서 미확정 사실이 요약 문장에 전부 노출되는지 케이스별 점검(오독 방지 요건).

**5. 확인 목록 블록** — `limit`·`registry.status`·`unknownItems`를 모으는 수집 함수 + 렌더. 항목 0개면 블록 미표시.
   - 검증: 단위 테스트(등기부 수신 시 첫 항목 탈락, 전부 해소 시 블록 없음 등 경계 케이스).

**6. 마무리 검수** — 전체 문구를 UX-03(해요체·능동·병기) 기준으로 통독, 350px에서 스크롤 길이 측정(목표: 접힘 닫은 상태 2화면 이내), WORKLOG 기록.
   - 검증: lint/test/build 전체 + 케이스 4종 스크린숏 비교.

단계 1·2는 화면 변화 없이 선행 가능하고, 3부터 화면이 바뀐다. 각 단계가 실패해도 이전 단계 상태로 동작한다.
